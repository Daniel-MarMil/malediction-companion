# ADR-13: The server as the source of truth for each account

- **Status:** Accepted
- **Date:** 2026-11-13 (replaces the design with decks and history on the phone and an optional copy on the server)
- **Reference:** section 10 of the architecture and requirements document, and "Deck synchronization" in section 9; RF-03 (withdrawn), RF-05, RF-27, RF-28 and RNF-02

## Context

Seekers League, the functional reference of the app, keeps every account's data on its server, so a player sees the same decks and history on any device. The previous design kept decks and history on the phone with an optional copy on the server: a player could not change phones or see the same data everywhere. The app must still work without a network: the deck builder, the history and local matches (RF-05, RF-27 and RNF-02).

## Decision

- As in Seekers League, the server stores each account's data and is its source of truth: decks, matches and history, and the community (events, tournaments, communities, the Meta and public decks).
- The card catalog comes from the server as signed packs (ADR-06).
- The phone keeps a copy to work without a network and synchronizes it when the connection comes back. A local match stays on the phone and is uploaded when there is a network (RF-28).
- Only the official cards that the server serves are used. Players cannot create their own cards: RF-03 was withdrawn on 2026-11-13.

When decks are synchronized, the server has the last word:

- **Concurrent changes:** every deck carries a version number. If two phones change the same deck without a network, the server rejects the change made on an old version: the phone keeps the server's version and saves its own as a copy of the deck, so nothing is lost.
- **Decks created without a network:** when the connection comes back, the server checks that all their cards are in its catalog, in some published version of the pack. If any card is not (for example, an unofficial card added by hand), it discards the deck with an error that marks those cards.
- **Cards with different data:** if the cards are on the server but their data on the phone does not match, the phone replaces them with the server's data, so its copy ends up the same.
- **Deck building rules:** synchronizing does not discard a deck that breaks the rules; it is saved with its validation state (RF-06 and RF-07), and the server validates it again before every match (RNF-09).

## Rejected alternatives

- Decks and history on the phone with an optional copy on the server (the previous design): it does not let a player change phones or see the same data everywhere.
- An app that only works online: it would break RF-05, RF-27 and RNF-02.

## Consequences

- The server starts in phase 1 with accounts, the catalog, decks and history (ADR-03 and ADR-05), so a hosting provider in the EEA is needed before anyone outside development uses it (ADR-07).
- The server's Catalog module publishes the signed packs; the app downloads them, checks them with `mc_pack_verify_trusted` and keeps them to work without a network (ADR-06).
- Card ids do not change between versions of the pack, because decks are checked against every published version.
- Without a license from Loot Studios there is no version to publish, because the app only uses the official cards (ADR-09 and ADR-12). Until then the server is private: only development and test accounts use it.
- The core does not change: it has no input/output and is the same library the server uses (ADR-01 and ADR-03). `mc_session_create` receives the pack as bytes, whether it comes from a file or from the server. A deck in the core only describes the warband; the stored deck's id, owner and version will live on the server and in the SQLite module, which do not exist yet.
- The SQLite module on the phone keeps the copy of decks and history and the queue of pending changes.
