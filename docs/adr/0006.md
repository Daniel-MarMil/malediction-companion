# ADR-06: Rules and cards as data packs signed with Ed25519

- **Status:** Accepted
- **Date:** 2026-11-07
- **Revision:** 2026-11-09: pack keys, `mc_pack_tool` and the trusted keys of the core
- **Revision:** 2026-11-13: the server's Catalog module serves the signed packs (ADR-13); pack format 2
- **Reference:** section 10 of the architecture and requirements document

## Context

The Malediction rules receive errata and revisions. Releasing the app for every rules change would be slow, and a tampered pack must not be accepted.

The core could check a signature against a key the app passed in, but nothing created keys or signatures, and the app had no list of keys to trust.

## Decision

Rules and cards travel as versioned data packs (`mc-rules-pack` format) with a detached Ed25519 signature that is checked with libsodium.

Keys and signatures (2026-11-09):

- **`mc_pack_tool`** (`tools/pack/`), a development tool in C++20 with libsodium, built with the same rules as the core. It is not part of `mc_core`, is not exported and is not built for Android or Windows.
  - `keygen NAME` creates an Ed25519 key pair. It asks for the password twice on the terminal without showing it, never through arguments or environment variables. It derives the encryption key with `crypto_pwhash` (Argon2id, `OPSLIMIT_SENSITIVE` and `MEMLIMIT_SENSITIVE`) and encrypts the secret key with `crypto_secretbox`. The secret key file (`NAME.mcsk`, mode 0600) is versioned JSON with the algorithm, the public key, the salt, the Argon2id limits, the nonce and the ciphertext. The public key goes in `NAME.pub`, in hexadecimal. It never overwrites a file and saves by default to `~/.config/seekers-companion/keys/`, outside the repository.
  - `sign` asks for the password, decrypts the secret key into protected memory (`sodium_malloc`, wiped with `sodium_memzero`) and writes the 64-byte detached signature that `mc_pack_verify` reads.
  - `verify` checks a pack and its signature against a public key file with `mc_pack_verify`.
- **Trusted keys in the core**: a short list of public keys compiled into the core (`core/src/trusted_keys.cpp`) and `mc_pack_verify_trusted`, which tries the pack against each one. Release builds trust only release keys, which do not exist yet. The development key is added only to Debug builds, through the CMake option `MC_TRUST_DEV_KEY`, which is on by default in Debug and refused in any other build type. It reads the public key from `keys/dev.pub` (`MC_DEV_PUBLIC_KEY_FILE`). `mc_pack_verify`, with the key as a parameter, stays as it was.

Format 2 (2026-11-13), which the official pack importer writes (ADR-12):

- **Factions:** a list of `{id, name}`. Every sigil of a card must be one of them; a card with no
  sigils is unaligned. The official ids are the short names of malediction.gg (`order`,
  `conclave`, `legion`, `primal`), and the names come from its pages.
- **Cards:** besides `id`, `name`, `type`, `rank`, `sigils` and, for a Legacy, `seeker` and
  `starting_echo`: `traits` and `abilities` (lists of text), `stats` (units only: `accuracy`,
  `power_hit`, `power_graze`, `range`, `speed`, `defense` and `max_health`, with the rulebook's
  names; each is a number or null (the card's dash, shown as –). A null stat is not 0: the unit
  cannot take actions that use it, and it can never be altered; range 0 means it attacks only
  nearby enemies), `image` (`file`, a path
  inside the pack folder; `sha256` of the file; and `source`, the URL it was downloaded from) and
  `source` (the card page). The signature covers the pack, and through each `sha256` the images
  too. `cost` and `rules_text` are null until the pack gives them: the pages do not show the cost,
  and the rules text is only in the card image.
- **Card ids:** ASCII letters, digits, `-`, `_` and `.`, up to 64 characters. An id never changes
  or is reused between versions of a pack, because decks are checked against every published
  version (ADR-13). The importer takes the slug of the card page the first time and keeps it in a
  registry tied to the page's post id, so a new slug keeps the id.
- **Official decks** (`decks`, RF-61): each with an `id`, a `name`, an optional Play Network `url`
  and a `deck` in the shape of `validate_deck`. They travel inside the pack because RF-61 takes
  their list from the official pack and they must match the cards of that version.
- Format 1 is no longer read: no published pack or app used it, and the test pack moved to
  format 2.

## Rejected alternatives

- Rules in the code: they force an app release for every erratum.
- OpenSSL or minisign to sign: another cryptography library and another file format, when the core already checks signatures with libsodium; `mc_pack_tool` signs and checks with the same code as the apps.
- Passwords from arguments or environment variables: they end up in the shell history, the process list or the environment of other processes.
- A secret key without encryption, protected only by file permissions: a copy or backup of the file would be enough to sign packs.
- The development key in every build: a release build would accept packs signed with a key that lives on a development machine.
- A single trusted key: changing it would leave out the apps already installed.
- Card ids from the card number in the image file name (for example `LEG-26`): the file name
  changes when an image is uploaded again. Ids from the order of the sitemap: they change when a
  card is added. Signing every image separately: one signature over the pack, which holds the
  hash of each image, covers them all.
- Official decks in a separate file: they would need their own signature and could drift from the
  cards of the pack.

## Consequences

- The core reads format 2 (`RulesPack::parse`), checks signatures against a given key (`mc_pack_verify`) and against the trusted keys (`mc_pack_verify_trusted`).
- Deck and copy limits come from the pack, not from the code.
- The secret keys never go into the repository: keygen writes them outside it, and `.gitignore` ignores `*.mcsk` as a safety net. A lost secret key or password cannot be recovered, so the owner keeps an offline backup of both.
- The development key is created by hand with `mc_pack_tool keygen dev`; its public key is copied to `keys/dev.pub`, which may be in the repository because it is public. Until then, Debug builds trust no key.
- Adding or changing a release key means editing `core/src/trusted_keys.cpp` and releasing the app; the list holds several keys so a new one can be added before the old one is retired.
- Opening a key file needs 1 GiB of memory and a few seconds. A file whose Argon2id limits are above the sensitive ones is rejected.
- The tests use deterministic keys from fixed seeds and the lowest Argon2id limits, never real keys.
- The server's Catalog module publishes the signed packs (ADR-13). The app downloads them, checks them with `mc_pack_verify_trusted` and keeps them to use without a network. Packs are imported and signed on the development machine, and the secret key never goes to the server.
- Card ids do not change between versions of a pack, because decks are checked against every published version (ADR-13).
